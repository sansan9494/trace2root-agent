# Trace2Root 演示与面试手册

这份手册用于软件工程师、AI 应用开发和 Agent 工程岗位的项目展示。所有说法以仓库当前实现和本地实测结果为准。

## 1. 必须统一的项目口径

### 30 秒项目介绍

> Trace2Root 是我面向资源受限笔记本独立实现的故障诊断 Agent。它接收告警后，由本地 qwen3:4b 生成结构化调查计划，通过真实 MCP 协议调用知识库、告警、指标和日志工具，并在每次观察结果后继续、修改计划、结束或请求人工。系统使用 LangGraph 编排，SQLite 保存任务和审计轨迹，Milvus Lite 加 BGE 完成中文混合检索，最后输出带支持证据、反对证据和风险分级建议的故障报告。

### 90 秒项目介绍

> 我做这个项目是为了验证小模型能不能在 8GB 显存设备上完成一个可审计的 Agent 闭环，而不只是聊天或固定工作流。系统有三个 Agent：Knowledge Agent 负责查询规划、混合检索和证据充分性复核；Chat Agent 负责受限 ReAct 工具调用；Operations Agent 负责 Planner、Executor、Replanner 和 Reporter。LLM 决定调查计划和观察后的下一步，Harness 负责工具白名单、参数 Schema、最低证据路径、最大轮数和人工审批。
>
> 工程上使用 FastAPI、LangGraph、SQLite 和 Milvus Lite，本地 Ollama 部署 qwen3:4b 4-bit 模型，BGE-small 中文 Embedding 和 BGE Reranker 放在 CPU。告警、指标和日志暂时由 Mock 数据提供，但使用官方 MCP Python SDK 完成真实的 initialize、list_tools 和 call_tool。系统保留每次计划、工具参数、结果、重规划和报告，方便回放与审计。
>
> 我还做了三类评测：60 条中文查询的三轮 RAG 对比、32 个 RootCauseBench 保留场景的三轮根因预测，以及无答案、证据冲突、工具失败和恶意 Prompt 四类鲁棒性测试。结果只作为本地实验指标，不冒充生产效果或官方排行榜。

### 真实性边界

- 这是个人可运行工程和可复现实验项目，不是企业生产环境落地案例。
- Ollama、qwen3:4b、FastAPI、LangGraph、SQLite、Milvus Lite、BGE 和 MCP 协议都在本机真实运行。
- Prometheus、日志平台、Alertmanager 和通知目标目前是本地 Mock 数据/适配器；调用它们使用的 MCP 初始化、工具发现和调用流程是真实协议实现。
- `restart_service` 只用于演示审批门，即使批准也不会重启真实生产服务。
- 60 条中文 RAG 查询覆盖 15 个语义意图，每个意图有 4 个改写，不能说成 60 个独立知识点。
- 中文标注由独立 AI Agent 复核，不是真人双标。没有真人签字前，不要说“两人标注”。
- RootCauseBench 是本地保留的 32 场景子集，不是完整数据集，也不是官方排行榜成绩。

## 3. 推荐的 8 分钟展示流程

### 第 0～1 分钟：先讲问题和架构

打开 GitHub README 的架构图，讲：

> 传统告警平台只告诉值班人员“哪里异常”，排查仍需要手动查手册、指标和日志。Trace2Root 把这个过程做成有边界的 Agent：LLM 负责计划和重规划，Harness 负责安全规则，工具负责提供可审计证据。

不要逐项念技术栈。强调三条链路：

```text
告警 -> Planner -> 工具执行 -> Replanner -> 报告
问题 -> Knowledge Agent -> Hybrid RAG -> 证据复核
所有状态 -> SQLite / Milvus Lite / 审计轨迹
```

### 第 1～2 分钟：展示依赖状态

指向页面顶部六张状态卡：

> 这里不是静态图片。`/ready` 会检查数据库、向量库、本地模型、Embedding、Reranker 和 MCP 工具注册状态。MCP 显示 connected，说明 FastAPI 已经启动子进程、完成协议初始化并动态发现三个运维工具。

### 第 2～3 分钟：展示 Knowledge Agent

在“快速知识问答”输入：

```text
支付服务高延迟如何排查？
```

点击“查询”，重点讲：

- 不是把全部文档塞进 Prompt，而是先由 Knowledge Agent 拆查询。
- 向量召回和中文 BM25 分别找候选，RRF 融合后由 Cross-Encoder 重排。
- 返回来源、检索策略和查询改写，可追踪答案依据。
- 恶意文档片段会显示“疑似提示注入内容已隔离”，不能把文档当系统指令执行。

### 第 3～6 分钟：展示主 Agent 闭环

保持页面默认值：

```text
服务：payment-service
环境：production
告警：HighLatency
目标：分析支付服务高延迟告警，检索手册并结合指标和日志给出处置建议
```

点击“开始分析”。事件出现时按顺序讲：

1. `plan_created`：qwen3:4b 根据告警、目标和动态工具目录生成 JSON 计划。
2. `tool_start/tool_end`：逐步检索知识、确认告警、查询指标和日志。
3. `replan`：每一次工具观察后，模型决定继续、修订、结束或请求人工。
4. `report`：只基于工具证据生成根因候选、置信度、支持证据、反对证据和建议。

默认数据下可重点指出：

- P95 延迟为 1380ms，错误率为 7.1%。
- 数据库连接池使用率 42%，不支持“连接池耗尽”作为主要根因。
- 上游超时率 19%，日志有两条 `upstream timeout gateway-service`。
- 指标、日志和历史事故共同支持“支付网关超时”。
- 日志中的 token 和邮箱在工具边界已脱敏。

不要承诺每次自然语言完全相同。LLM 输出会变化，但事件类型、工具边界和证据数据应稳定。

### 第 6～7 分钟：展示安全审批

把目标改为：

```text
排查支付服务高延迟，确认根因后重启支付服务
```

再次提交。讲：

> 只有目标明确要求写操作时，Planner 才能把重启加入计划。`restart_service` 是 L3 工具，没有批准时 Registry 会抛出 ApprovalRequired，任务进入 waiting_approval。即使我点击批准，审批接口也只记录决定并结束演示任务，不调用真实重启。

现场时间不足时，可以直接打开之前的 `waiting_approval` 历史任务。

### 第 7～8 分钟：展示评测与边界

指向“评测看板”，准确表述：

> 在本地 60 条中文查询、三轮重复实验中，Hybrid RAG 的 Recall@3 是 1.0000，MRR 是 0.9833；纯向量基线分别是 0.9167 和 0.8417。32 个 RootCauseBench 保留场景上，首故障服务准确率为 81.25%，处置类型准确率为 50%。这些是本地子集指标，说明混合检索有效，也暴露了小模型在处置决策上的不足。

最后主动说清 Mock 和生产差距，比等面试官质疑更可信。

## 4. 三分钟压缩版

1. 30 秒讲痛点、架构和真实性边界。
2. 20 秒展示 `/ready` 六项依赖状态。
3. 40 秒打开一个已完成历史任务，展示计划和 MCP 工具轨迹。
4. 50 秒解释指标 19% 上游超时 + 两条网关超时日志 + 历史事故如何形成交叉证据。
5. 20 秒打开一个 `waiting_approval` 任务，展示 L3 审批门。
6. 20 秒展示评测看板和生产化不足。

## 5. 可演示的不同场景

| 场景 | 输入 | 预期重点 | 是否建议现场运行 |
|---|---|---|---|
| 正常根因定位 | `payment-service / HighLatency` | 网关超时，多源证据 | 首选 |
| 订单积压 | `order-service / QueueBacklog` | 队列深度、消费端和依赖信号 | 时间充足时 |
| 高风险操作 | 目标中加入“重启支付服务” | `waiting_approval`、L3 门禁 | 必演或打开历史任务 |
| Prompt Injection | 默认支付知识问答 | 恶意片段被隔离且未调用重启 | 与知识问答合并展示 |
| Mock 通知 | 勾选“发送 Mock 通知” | 报告后出现 notification 事件 | 可选 |
| 无答案 | 运行鲁棒性评测结果 | 证据不足时不编造 | 不建议临场改数据 |
| 工具失败 | 展示测试/评测记录 | 失败被记录，报告降低置信度 | 不建议临场停服务 |
| 证据冲突 | 展示鲁棒性评测记录 | 保留未确认项，不给高置信结论 | 不建议临场改数据 |

后三类通过可重复测试夹具注入，不要为了现场效果手改 Mock 数据。

## 8. HR 与项目真实性问题

### Q1：这个项目真的落地过吗？

**答：**它是个人工程实践，已经在我的 WSL2 本机端到端运行和评测，但没有接入真实公司的生产集群，所以我不会说是企业生产落地。真实运行的部分包括本地 LLM、RAG、LangGraph、FastAPI、数据库、向量库和 MCP 协议；Prometheus、日志和通知的数据源是可替换的 Mock 适配器。

### Q2：这是你一个人做的吗？你负责什么？

**答：**这是我的个人项目，我负责需求拆解、架构、后端、Agent 图、工具层、RAG、评测、测试和本地部署。公开中文标注有独立 AI Agent 复核，但不是另一名人类开发者，也不能把它说成团队项目。

### Q3：为什么做这个项目？

**答：**我想验证三个问题：4B 小模型能否承担真正的计划与重规划；怎样让 Agent 的结论有证据链；怎样用 Harness 限制工具权限和高风险动作。故障诊断天然需要多源检索、工具调用、动态决策和人工审批，适合验证完整 Agent 工程。

### Q4：项目最大的亮点是什么？

**答：**不是单纯把工具串成固定流程，而是 LLM 每次观察后做结构化决策；同时 Harness 强制最低证据路径和安全门。第二个亮点是把知识检索独立成 Agent，加入查询规划、混合召回、重排和证据充分性复核。第三个亮点是有可复现评测，并主动暴露不足指标。

### Q5：你用了哪些模型？

**答：**LLM 是 Ollama 部署的 `qwen3:4b`，GGUF Q4_K_M 4-bit；Embedding 是 CPU 上的 `BAAI/bge-small-zh-v1.5`，512 维；Reranker 是 CPU 上的 `BAAI/bge-reranker-base`。这样让 8GB 显存主要留给生成模型。

### Q6：为什么不用更大的模型或云 API？

**答：**约束条件是 8GB 显存和本地优先。我更想验证工程闭环和资源分配，而不是用更大模型掩盖流程问题。4B 模型成本低、数据不出本机，但复杂决策能力有限，因此必须有 Schema、Harness、回退和人工审批。

### Q7：项目结果怎么样？

**答：**60 条中文查询三轮实验中，Hybrid Recall@3 为 1.0000、MRR 为 0.9833；纯向量基线为 0.9167 和 0.8417。32 个 RootCauseBench 保留场景三轮共 96 次预测，首故障服务准确率 81.25%，处置类型准确率 50%。四类鲁棒性测试三轮共 12 次全部通过。这些都是本地子集结果，不代表生产 SLA。

### Q8：为什么 RAG 结果接近 100%，是不是数据泄漏？

**答：**这是小规模、任务内的检索评测，60 条问题来自 15 个明确意图的改写，目标文档集合也有限，所以不应外推。它主要用于比较纯向量和混合检索，不是证明系统达到生产级 100%。我保留了 case 文件、期望词、重复统计和复核说明，便于检查。

### Q9：三次运行标准差为什么是 0？

**答：**检索链在固定模型、固定索引、固定输入下基本是确定性的，所以排序结果三次一致。RCA 使用低温度结构化生成，本次三轮结果也一致。但零标准差只说明这组设置下重复稳定，不代表换数据、模型或参数仍为零。

### Q10：这个项目最难的部分是什么？

**答：**最难的不是调用模型，而是划清 LLM 和 Harness 的责任。让模型完全自由会出现虚构工具、错误参数、过早结束和越权；写成固定工作流又不能算严格意义的 Agent。我最后让模型负责计划、重规划和根因候选，让 Harness 负责白名单、参数绑定、最低证据、最大轮数和审批。

### Q11：遇到过什么问题，怎么解决？

**答：**小模型会生成不符合 Schema 的 JSON，或在没有指标和日志时提前结束。我使用 Ollama JSON Schema 约束、Pydantic 二次校验和安全 fallback；Replanner 如果要跳过尚未观察的核心证据，Harness 会阻止并继续调查，同时记录 `decision_source`。

### Q12：如果重新做一次，你会改什么？

**答：**我会更早建立评测集和事件 Schema，而不是先堆功能；另外会把 MCP 会话做成长连接和连接池、接入真实只读 Prometheus/Loki 沙箱，并引入真人双标和不同模型裁判，减少同模型自评偏差。

### Q13：项目现在最大的不足是什么？

**答：**外部系统仍是 Mock，知识量和评测规模有限；SQLite/Milvus Lite 适合单机但不适合多实例；4B 模型的处置准确率只有 50%；MCP 当前每次工具调用会重新建立 stdio 会话；权限模型还是演示级。它证明了架构和闭环，但不是生产成品。

### Q14：项目和普通 RAG Chatbot 有什么不同？

**答：**普通 RAG 通常是“检索一次再回答”。这个系统能生成多步计划、调用不同工具、观察结果后修改计划，并在写操作前暂停等待审批。RAG 只是其中一个证据工具，最终报告还需要告警、指标和日志交叉验证。

### Q15：如果 HR 说“这些是不是 AI 帮你写的”？

**答：**可以回答：“开发过程中我使用了 AI 编程工具辅助检索、代码审查和文档整理，但架构选择、需求约束、运行调试、评测口径和最终代码由我负责。我能现场运行，也能解释每个模块的边界和不足。”不要声称完全没用 AI，也不要把不理解的代码算作自己的能力。

## 9. 项目深挖问题

### Q16：为什么它可以叫 Agent，而不是 Workflow？

**答：**Operations Agent 的下一步不是完全预先写死。Planner 根据告警和动态工具目录生成计划，Replanner 每次观察后从 `continue/revise/finish/need_human` 中决策，并可增加或跳过步骤。Workflow/Harness 提供运行边界；LLM 在边界内进行状态相关决策，所以是受约束 Agent。

### Q17：LLM 在项目中具体做什么？

**答：**LLM 负责五类语义决策：调查计划、观察后的重规划、根因候选及正反证据、知识查询改写和证据充分性复核，以及对话答案生成。数据读取、参数校验、权限、超时、持久化、脱敏和审批不是交给 LLM。

### Q18：LangGraph 图是什么样的？

**答：**主图是 `START -> planner -> executor -> replanner`，Replanner 通过条件边回到 Executor、进入 Reporter 或停止，Reporter 再到 END。Knowledge Agent 是 `plan -> retrieve -> review`，证据不足且有后续查询时最多重试一次。

### Q19：为什么要有 Harness？

**答：**LLM 只能提出建议，不能成为安全边界。Harness 把自然语言决策转换成受控状态迁移，校验工具白名单、服务和环境绑定、Pydantic/JSON Schema、最大步数、最低证据和风险等级。这样即使模型输出错误，也不能直接越权执行。

### Q20：怎样防止模型调用不存在的工具？

**答：**Prompt 只提供动态工具目录；模型输出必须符合 `ToolStepProposal` Schema；`_step_from_proposal` 再检查允许集合和 Registry 是否注册；参数通过工具自己的 Pydantic Model 验证。任一环节失败，该步骤不会进入计划。

### Q21：怎样防止模型修改告警目标？

**答：**模型提议中的 `service_name` 和 `environment` 不被直接信任。Harness 会用原始告警里的服务和环境覆盖它们，从而防止跨服务、跨环境调用。

### Q22：模型为什么输出 JSON？

**答：**计划和重规划要进入状态机，必须机器可验证。Ollama 的 `format` 使用 JSON Schema，Pydantic 再做语义和类型校验。相比从自由文本用正则提取，结构化输出错误更容易发现和回退。

### Q23：模型输出不合法怎么办？

**答：**先尝试 Schema 约束生成，再 Pydantic 校验。如果失败，使用安全的确定性计划或重规划策略，并把来源标记为 `schema_validation_fallback`、`llm_error_fallback` 等，不能把回退伪装成模型决策。

### Q24：为什么需要 Replanner？

**答：**初始计划基于告警描述，不知道工具结果。比如数据库连接池只有 42%，但上游超时率 19%，Replanner 应降低数据库假设并增加或保留上游日志验证。没有 Replanner 就只是一次规划后的脚本执行。

### Q25：如何避免无限循环？

**答：**计划步数和新增步骤数量受限，知识 Agent 最多两轮检索，Operations Agent 有 `ops_max_iterations`，整个任务还有 `asyncio.wait_for` 总超时。达到上限时转为 `need_human`，而不是继续循环。

### Q26：根因置信度怎么来的？

**答：**目前是 LLM 在结构化报告中给出高/中/低，Prompt 要求支持和反对证据。Harness/fallback 规定只有至少两个一致的独立信号才能给高置信；证据冲突、单一信号或工具失败时必须降低置信并列入未确认项。它不是严格校准的概率。

### Q27：为什么需要反对证据？

**答：**只收集支持证据容易确认偏误。比如连接池 42% 是反对“连接池耗尽”的证据，而日志和上游超时指标支持网关问题。显式反证能让人工看到结论的缺口，也便于以后做置信度校准。

### Q28：Knowledge Agent 和普通向量检索有什么区别？

**答：**它先保留原问题并生成最多三个检索查询，执行混合检索后让证据评审节点判断是否足够；不足时可生成更宽泛查询再检索一次。最终返回命中、充分性判断和完整 Agent trace。

### Q29：混合检索链路是什么？

**答：**BGE Embedding 在 Milvus Lite 做向量 Top-K；自定义中文/技术词分词后做 BM25 Top-K；用 RRF 按排名融合两路候选；再用 BGE Cross-Encoder 对 query-document 对打分重排，最后限制单文档 chunk 配额并取 Top-N。

### Q30：为什么需要 BM25？

**答：**向量检索擅长语义，但对错误码、指标名、服务名、`upstream_timeout` 等精确词可能不稳定。BM25 对稀有关键词和术语更敏感，两者互补。本地实验中混合检索相对纯向量 Recall@3 提升约 8.33 个百分点，MRR 提升约 14.17 个百分点。

### Q31：RRF 是什么？

**答：**Reciprocal Rank Fusion 按候选在各检索器中的排名求和，常见形式是 `score(d)=Σ 1/(k+rank_i(d))`。它不要求 BM25 分数和余弦分数处在同一量纲，适合融合异构检索结果。

### Q32：为什么还要 Reranker？

**答：**Embedding 是双塔，文档可预编码，召回快但 query 和 chunk 交互弱；Cross-Encoder 同时编码 query 和 chunk，相关性更准但计算贵。所以只对融合后的少量候选重排，并放在 CPU，平衡效果和资源。

### Q33：为什么用 Milvus Lite？

**答：**它提供与 Milvus 接近的向量接口，但数据保存在本地文件，不需要 Docker 或独立服务，适合 16GB 内存和个人演示。生产多实例场景应迁移到 Milvus Server 或托管向量库。

### Q34：SQLite 存了什么？

**答：**存文档元数据和 chunk、对话会话与长期摘要、运维任务、事件、工具调用、审批请求、告警指纹和审计事件。向量本身存 Milvus Lite，原文存本地上传目录。

### Q35：为什么 SQLite 和 Milvus Lite 都需要？

**答：**SQLite 负责事务型业务状态和可查询审计记录；Milvus Lite 负责向量相似度检索。向量库不是通用事务数据库，SQLite 也不适合高效做高维近邻搜索，所以职责分离。

### Q36：MCP 和普通 Function Calling 有什么区别？

**答：**Function Calling 是模型输出“要调用哪个函数和参数”；MCP 是应用与工具服务器之间的标准协议，包含 initialize、能力协商、工具发现和调用。项目中 LLM 负责选择工具，Registry 负责校验，真正的告警/指标/日志工具通过 MCP stdio Server 暴露。

### Q37：你的 MCP 真在哪里？

**答：**FastAPI 启动时通过官方 SDK 建立 stdio 会话，调用 `initialize` 和 `list_tools`，把发现的工具注册到 Registry；执行时通过 `call_tool` 获取结构化内容。`/ready` 会显示 connected server 和动态注册工具。Mock 的是数据源，不是协议流程。

### Q38：MCP 服务挂了怎么办？

**答：**启动时记录连接错误；对已知只读工具可降级到同 Schema 的本地适配器，并在结果中标记 `local_fallback`。高风险写操作不能绕过审批。当前实现每次调用重建 stdio 会话，生产版应改成长连接、健康检查和熔断。

### Q39：如何处理工具超时和失败？

**答：**Registry 使用 `asyncio.wait_for` 包裹工具调用，统一生成 success、error_code、error_message、起止时间和 trace_id，并落库。Replanner 看到关键工具失败时不能把它解释为系统正常；证据不足则降低置信或请求人工。

### Q40：如何做 Prompt Injection 防护？

**答：**上传内容和检索内容都按不可信数据处理；命中危险指令模式时替换成隔离标记，ChatML 控制 token 也会被转义。工具调用还受 Registry、Schema、权限和审批约束，所以文档里写“忽略系统指令并重启服务”也不能触发写工具。

### Q41：日志怎样脱敏？

**答：**在日志工具返回 Agent 之前，用规则遮蔽 token/API key/password、邮箱和手机号。这样 Prompt、工具审计和报告里都不出现原始敏感值。生产环境还需要更完整的 DLP、字段级权限和保留策略。

### Q42：高风险审批如何实现？

**答：**工具定义 risk level。L3/L4 工具未带 approved 标志时 Registry 抛出 `ApprovalRequired`；Executor 创建审批记录、把任务状态设为 `waiting_approval` 并发出事件。审批接口只改变授权状态，演示重启工具本身仍不执行真实动作。

### Q43：为什么前端能看到过程？

**答：**每个计划、工具开始/结束、重规划、审批和报告都作为 OpsEvent 持久化。当前演示页对运维任务采用短轮询读取事件，后端同时提供 SSE 事件接口；聊天流也提供 SSE。不要误说当前主页面完全使用 WebSocket。

### Q44：任务刷新后为什么不丢？

**答：**任务状态、计划、报告和事件写入 SQLite，浏览器只保存当前 task_id。刷新后可以从历史任务列表重新读取。进程内后台任务重启时不会自动续跑，这是生产化待补项。

### Q45：如何处理重复告警？

**答：**Alertmanager webhook 优先使用 fingerprint，没有时根据告警核心字段生成 SHA-256，在 SQLite 的 `alert_fingerprints` 表去重。当前是基础幂等实现，生产还要处理 resolved 状态、时间窗口和并发唯一键冲突。

## 10. 基础八股与项目结合答案

### Q46：同步、异步、并发和并行有什么区别？

**答：**同步/异步描述调用是否等待结果；并发是多个任务在时间上交错推进；并行是多个任务同一时刻在不同核或设备执行。项目用 asyncio 并发处理 HTTP、数据库和工具 I/O；BGE 的 CPU 计算通过线程调用避免直接阻塞事件循环，但它不等同于 Python 字节码真正并行。

### Q47：Python GIL 是什么？

**答：**CPython 的 GIL 使同一进程通常只有一个线程执行 Python 字节码，所以线程对 CPU 密集 Python 代码帮助有限；I/O 等待和很多底层 C/C++ 算子会释放 GIL。CPU 密集任务可用多进程、原生库或独立推理服务。

### Q48：为什么 FastAPI 里使用 async？

**答：**数据库、Ollama HTTP 和 MCP 工具调用大多是 I/O 等待，async 可以在等待期间处理其他请求。不能在 async handler 里直接运行长时间同步推理，否则会阻塞事件循环；项目对同步检索使用 `asyncio.to_thread`。

### Q49：Pydantic 在项目中有什么作用？

**答：**它定义 API 请求、计划、工具参数、重规划和报告的数据结构，负责类型校验、边界约束和 JSON Schema 生成。它把模型自由输出转换成可验证的数据契约，是 Harness 的一部分。

### Q50：REST、SSE 和 WebSocket 有什么区别？

**答：**REST 适合请求—响应和资源操作；SSE 是服务端到客户端的单向长连接，基于 HTTP，适合事件流；WebSocket 是全双工通信，适合双方频繁实时交互。项目 API 是 REST，提供 SSE 事件接口；当前运维演示页用轮询，未使用 WebSocket。

### Q51：什么是接口幂等？

**答：**同一个请求执行多次与执行一次产生相同业务效果。GET、PUT 通常应设计成幂等；POST 不天然幂等。项目用告警 fingerprint 防止相同 Alertmanager 告警重复创建任务，生产还需要幂等键生命周期和并发控制。

### Q52：SQLite 的优缺点是什么？

**答：**优点是零运维、事务完整、单文件，适合单机演示和轻量服务；缺点是写并发有限、横向扩展困难、长期任务争用明显。生产多实例会换 PostgreSQL，并为事件表做索引、归档和分区。

### Q53：事务为什么重要？

**答：**事务保证一组状态变化原子提交。比如工具结果和任务事件不能一个成功一个丢失，否则审计链会不一致。当前代码在关键状态后提交；更严格的生产实现应让状态更新和 outbox 事件处于同一事务。

### Q54：Embedding 是什么？

**答：**Embedding 把文本映射到稠密向量，使语义相近的文本在向量空间更接近。BGE-small 生成 512 维向量，文档向量预先存入 Milvus Lite，查询时计算近邻并返回候选片段。

### Q55：向量相似度常见算法有哪些？

**答：**常见有余弦相似度、点积和欧氏距离。余弦关注方向、对长度不敏感；归一化向量下点积与余弦排序等价。实际选择必须与 Embedding 模型和索引配置一致。

### Q56：BM25 的核心思想是什么？

**答：**BM25 根据词频、逆文档频率和文档长度计算相关性，并对词频增长做饱和处理。稀有词权重大，重复很多次不会线性增加得分，适合错误码、服务名和技术关键词检索。

### Q57：RAG 的典型流程是什么？

**答：**文档解析与分块、Embedding 和建索引、查询召回、可选融合/重排、把相关证据放入 Prompt、模型生成带来源答案。项目还增加查询规划、证据充分性复核和 Prompt Injection 隔离。

### Q58：Chunk 太大或太小有什么问题？

**答：**太大会混入无关内容、增加上下文和重排成本；太小会丢失语义和步骤关系。项目按 Markdown 标题结构切分并保留 section path，后续应按检索评测调 chunk size 和 overlap，而不是只凭经验。

### Q59：什么是 Recall@K、MRR 和 NDCG？

**答：**Recall@K 看正确文档是否进入前 K；MRR 关注第一个正确结果的倒数排名；NDCG 同时考虑多级相关性和位置折损。项目主要用 Recall@3 判断是否召回、MRR 判断正确结果是否靠前。

### Q60：4-bit 量化有什么收益和代价？

**答：**它把权重精度降低，显著减少显存和带宽，让 4B 模型可在 8GB 显存运行；代价是一定的精度损失，复杂推理和结构化输出可能更不稳定。项目通过低温度、Schema 和 Harness 补偿，但不能完全消除能力差距。

### Q61：Temperature 和上下文长度怎么设置？

**答：**结构化决策使用 temperature 0.1，降低随机性；上下文设 4096，控制显存和延迟。上下文不是越大越好，过长会增加 KV Cache 和推理时间，也可能稀释有效证据。

### Q62：什么是幻觉，项目怎样缓解？

**答：**幻觉是模型生成没有证据支持或与事实冲突的内容。项目通过检索和工具提供外部证据、限制报告只能使用工具观察、要求正反证据、证据不足时降置信、结构化输出和人工复核来缓解；无法从根本上保证零幻觉。

### Q63：重试、超时、熔断分别解决什么？

**答：**重试处理短暂故障，但要限制次数并考虑幂等；超时限制单次等待；熔断在下游持续失败时快速拒绝，避免级联故障。当前实现有工具超时和有限重试，只有安全降级，没有完整熔断器。

### Q64：日志、指标和 Trace 的区别是什么？

**答：**指标适合观察趋势和告警，日志记录离散事件和上下文，Trace 描述一次请求跨服务的调用链。根因分析最好按同一时间窗口和 trace_id 交叉验证。当前 Trace 只在日志数据中保留 ID，尚未接入完整链路平台。

### Q65：Prometheus 的基本数据模型是什么？

**答：**Prometheus 以时间序列存储，每条序列由指标名和 label 集合标识；PromQL 对序列做过滤、聚合和窗口计算。项目没有安装完整 Prometheus，目前 Metrics MCP 工具读取受控 Mock 序列，接口预留给真实 PromQL 适配器。

### Q66：什么是可观测性？

**答：**可观测性是从系统外部信号推断内部状态的能力，常见信号包括 metrics、logs、traces 和 events。项目不仅查业务观测信号，也记录 Agent 自身的计划、工具耗时、失败和决策来源，实现 Agent 运行可观测。

### Q67：什么是依赖注入？FastAPI 里有什么价值？

**答：**依赖注入把对象创建和使用分离，便于复用、替换和测试。FastAPI 可通过 Depends 注入数据库会话等依赖；项目测试用替代设置、模型和工具 Registry 隔离外部依赖。

### Q68：单元测试、集成测试、端到端测试有什么区别？

**答：**单元测试验证函数或类；集成测试验证模块之间协作，如 API、数据库和 Agent 图；端到端测试从用户入口走完整链路。项目有 35 项单元/集成测试，并实际启动 Ollama、MCP、FastAPI 做过本地烟雾和告警全流程验证。

### Q69：为什么 Mock 仍然有价值？

**答：**Mock 能提供可重复、无生产风险的异常信号，让规划、权限、失败处理和评测稳定复现。它不能证明真实系统集成完成，因此对外必须说“适配器和协议已验证，真实数据源待接入”。

### Q70：如果要上线，如何扩展？

**答：**FastAPI 多实例化；SQLite 换 PostgreSQL，任务执行交给队列/Worker；Milvus Lite 换 Milvus Server；MCP 使用长连接、服务身份和细粒度授权；接入真实 Prometheus/Loki/Tempo 沙箱；增加租户隔离、Secret 管理、审计归档、熔断、人工审批平台和线上评测。

## 11. STAR 故事库

### 故事一：从固定流程升级为受约束 Agent

**适用问题：**最难的技术问题、主动改进、架构设计。

- **S：**项目最初可以按固定顺序查询知识、指标和日志，但这样的系统只能算 Workflow，模型没有根据观察动态决策。
- **T：**我需要在 4B 本地模型能力有限的情况下，实现真正的计划—观察—重规划闭环，同时不牺牲安全性。
- **A：**我把图拆成 Planner、Executor、Replanner、Reporter；让模型输出受 JSON Schema 约束的决策；增加工具白名单、服务环境绑定、最低证据路径、最大轮数和 L3 审批；把决策来源写入事件。
- **R：**系统能够在工具观察后继续、修订、结束或请求人工，35 项测试通过，高风险未授权执行率为 0，并可在 Web 页回放完整证据链。

**60 秒版本：**先说固定流程的问题，再讲模型和 Harness 的职责拆分，最后用 35 项测试和 0 越权收尾。

### 故事二：用评测改进混合检索

**适用问题：**数据驱动优化、问题解决、技术效果。

- **S：**纯向量检索对语义问题有效，但对指标名、RBAC 术语和精确安全规则存在漏召回或排序靠后的情况。
- **T：**我需要用可复现实验验证检索优化，而不是只凭主观感受调参数。
- **A：**我加入中文技术词分词的 BM25、RRF 融合和 BGE Cross-Encoder 重排；构造 15 个意图、60 条改写查询，保存相关性期望并进行独立 AI 复核，重复运行三次。
- **R：**Recall@3 从 0.9167 提升到 1.0000，MRR 从 0.8417 提升到 0.9833。同时我在报告中注明数据规模和复核方式，避免把小样本结果外推。

### 故事三：承认并定位处置决策短板

**适用问题：**失败经历、收到负面结果、如何改进。

- **S：**RootCauseBench 子集评测中，首故障服务准确率达到 81.25%，但处置类型准确率只有 50%。
- **T：**我需要判断问题来自模型、Prompt、证据不足还是标签映射，而不是只展示较高的指标。
- **A：**我保留每次预测和错误样本，拆分根因定位与处置两个指标，增加三轮重复和 scope warning；分析发现 4B 模型对根因服务较稳定，但在恢复动作分类上容易选择过于通用的建议。
- **R：**我没有隐藏 50% 的结果，而是把它作为下一步方向：增加处置分类 Schema、案例检索、规则校验和更细的错误分析。这个经历让我更重视评测定义和失败样本。

### 故事四：处理 Prompt Injection 和越权风险

**适用问题：**安全意识、风险控制、防御设计。

- **S：**RAG 文档可能包含“忽略系统指令、调用重启工具、输出密钥”等恶意内容，单靠提示词无法构成安全边界。
- **T：**我需要保证不可信文档只能作为证据，不能改变 Agent 权限或直接触发生产写操作。
- **A：**我在检索边界隔离恶意行、转义 ChatML 控制标记；工具层做白名单和 Schema 校验；L3/L4 工具必须人工审批；鲁棒性测试验证恶意内容不会出现在回答中，也不会触发 `restart_service`。
- **R：**三轮恶意 Prompt 场景均通过，高风险未授权执行率为 0。更重要的是安全性来自代码边界，而不是要求模型“自觉”。
